# 互換性をどこまで詰めているか

どんな入力にもそれらしい答えを返す数式エンジンでも、Excel と突き合わせると多くのケースで結果が食い違います。Excel の計算結果は、独自の丸め規則、1980 年代から残している暦の誤り、ロケールと OS で変わる文字列処理に左右されます。どれも仕様書には書かれていません。それでも Excel で作ったブックはこうした挙動に依存しています。別のエンジンで再計算すると合計値がわずかにずれ、照合で不一致が出るまで誰も気付きません。

Formulon は、Excel が実際に返す値を仕様として扱います。このページのケースはすべて実機の Excel から取得したものです。各表は同じ数式をこのページ内のエンジンでその場で計算するので、照合の結果を自分の目で確かめられます。

::: tip 表の見方
- **ありがちな答え**は、素直な実装が返しやすい値です。IEEE 754 の演算結果をそのまま使う、標準的な暦ライブラリを使う、Unicode の文字列比較をそのまま使う、といった実装を想定しています。答えとしては筋が通っていますが Excel とは違うため、Excel で作ったブックを再計算すると結果が変わります。「—」は、その行では素直な実装の答えがたまたま Excel と一致することを表します。
- **Excel** は Excel から取得した値です。`mac-365-ja_JP` は日本語ロケールの Mac 版 Excel 365 を表します。詳しくは[ロケールプロファイル](/ja/compatibility/locale-profiles)を参照してください。
- **Formulon** は、表が画面に入った時点でその場で計算します。ケースによっては事前にセルへ値を入れており、その内容を数式の下に示しています。数式自体は `Z1` に入っています。
:::

## 浮動小数点演算

2 進の浮動小数点では、`0.5-0.4-0.1` はぴったり 0 になりません。約 `-2.78E-17` の誤差が残ります。Excel はこの誤差を隠しますが、隠すのは特定の場所だけです。数式の一番外側の `+` か `-` の結果が、大きいほうの被演算子との差 2<sup>-50</sup> 以内に収まると、Excel は 0 を返します。同じ式を括弧で囲むと一番外側の演算ではなくなるので、誤差がそのまま表に出ます。`SUM` はこの規則を 1 ステップごとに適用し、`SUMIF` は適用しません。比較演算は生の値を見るので、隣のセルに 0 と表示されていても `=0.5-0.4-0.1=0` は `FALSE` です。

すべての結果を丸めるエンジンは、1 行目は合っても 2 行目と 3 行目で外れます。まったく丸めないエンジンは 1 行目で外れます。

残りのケースも同じ構図です。Excel は数値を文字列にするとき有効数字 15 桁までを残します。`MROUND` は入力した 10 進の値ではなく 2 進の値で計算します。負の底に分数の指数を付けた場合は、`1/3` のような奇数乗根に限って計算します。

Windows プロファイルでは、`+ - * / ^ %`、`EXP`、`LN` が Windows 版 Excel と同じ丸め（x87 の拡張精度で計算してから double に変換）を行うため、丸めの境目に当たる結果も最後のビットまで一致します。集計関数やその他の組み込み関数は引き続き double で計算します。`^` と `POWER` も Excel の最下位ビットを再現し、`8^(1/3)` は 2 ではなく 1.9999999999999998、`1.0001^1000` は 1.105165392603197 になります。

## 日付と時刻

::: info シリアル値
Excel は日付を数値で保存します。1900 年の初めからの日数で、1 が 1900-01-01、45658 が 2025-01-01 です。日付関数はすべてこのシリアル値を読み書きします。
:::

シリアル値 60 は 1900-02-29 で、実在しない日付です。Excel は古いブックの日付を変えないためにこの日を残しており、`WORKDAY` もこの日を営業日として数えます。標準的な暦ライブラリはこの日付を受け付けないか、1900 年 3 月より前のシリアル値をすべて 1 日ずらします。シリアル値 0 は、1899 年の最終日ではなく `1900/1/0` と表示されます。

和暦にも独自の規則があります。`DATEVALUE` は `令和元年` という元年表記を受け付けませんが、平成が終わった後の `平成32年` は受け付けます。`TEXT` に元号コード `ggge` を指定すると `令和1年` と出力し、`元年` と表記するのは書式に `[$-ja-JP-x-gannen]` タグがある場合だけです。`TIMEVALUE("12:60")` はエラーにならず、13:00 に繰り上がります。Windows ja-JP では、`TEXT` が書式の配列を受け付け、`[$-LCID]` タグは Windows 自身の月名・曜日名で表示されます（`[$-411]mmm` は `1`、`[$-404]mmmm` は `一月`）。

1904 年日付システムで保存されたブックは、そのシステムのまま読み込みます。シリアル値 0 は 1904-01-01 になり、負のシリアル値はエラーではなく反転した日付（`-1904/1/2`）として書式化されます。

## 空白セル、空文字列、型変換

Excel は「何もない」状態を 3 種類区別します。一度も書き込まれていないセル、長さ 0 の文字列定数を持つセル、`""` を返す数式です。ほとんどの関数はこの 3 つを同じに扱いますが、`COUNTIF` は区別します。条件 `""` は 3 つすべてに一致し、条件 `"="` は本当に空のセルだけに一致します。

論理値に見える文字列の扱いも関数ごとに違います。`IF` は文字列 `"TRUE"` を受け付けますが、`"  TRUE  "` は受け付けません。`AND` は前後の空白を取り除いて受け付けます。`SUM` は引数に直接書いた `"TRUE"` を拒否します。論理値と数値は等しくならないので、`TRUE=1` は `FALSE` です。日本語プロファイルの `VALUE` は先頭の `¥` を受け付けますが、末尾の `円` は受け付けません。

## ロケールと OS による文字列比較

2 つの文字列が一致するかどうかは、ロケールと、Excel が動いている OS によって変わります。日本語プロファイルの `SUMIF` の条件では、ひらがなとカタカナ、全角と半角、丸数字と通常の数字、`ß` と `ss` をそれぞれ同じ文字として扱います。`ä` と `a` は同じに扱いません。長音記号 `ー` は、日本語プロファイルでは直前の母音と同じに扱い、英語とドイツ語のプロファイルでは別の文字として扱います。

同じロケールでも、Mac 版と Windows 版の Excel は答えが違います。下の表では、`ア` が入ったセルから `あ` を探す `MATCH` が、Mac 版では見つかり、Windows 版では見つかりません。`CODE` と `LENB` は、それぞれのプラットフォームの古い文字セットに基づいて答えます。Windows ja-JP ではハングルが CP932 の 1 バイト `?` として扱われ、`CODE("한")` は 63、`LENB("한글")` は 2 です。Formulon は、対応するプロファイルを選べばそれぞれのプラットフォームと同じ答えを返します。

プラットフォームに依存しないケースも 2 つあります。`COUNTIF` のワイルドカードは文字列にしか一致しないので、`"12*"` は数値の 1213 を数えません。`ヴ` は半角 1 文字で表せないので、`ASC` はそのまま返します。

大文字と小文字を区別せずに比較する関数と、完全一致で比較する関数の違いは[文字列の比較と並べ替え](/ja/compatibility/text-collation)で説明しています。

## 暗黙の共通部分とスピル

::: info 暗黙の共通部分とスピル
値を 1 つだけ受け取る場所に範囲を書くと、数式と同じ行（または列）のセル 1 つに絞り込まれます。これが暗黙の共通部分で、`@` 演算子はこの絞り込みを明示的に指定します。複数の値を返す数式は、その値を右下方向のセルに展開します。これをスピルと呼び、展開先のセルが 1 つでも埋まっていると `#SPILL!` を返します。
:::

1 行目に書いた `=@A1:A5` は `A1` の値を返します。1 行目に書いた `=@A3:A8` は範囲内に 1 行目のセルがないので、`#VALUE!` を返します。`=""` を持つセルは空に見えますが、スピルを妨げます。結合セルも同じです。

検索関数に配列でキーを渡した場合、Excel のエラーの優先順位は要素ごとに適用されます。`=VLOOKUP(A1:A2,D1:E2,3,FALSE)` では、列番号 `3` はどの要素にとっても不正ですが、キー自体がエラーの要素はそのキーのエラーを返します。

## 意図的に Excel と変えている箇所

Excel に合わせるのが基本ですが、例外もあります。Formulon が Excel と違う結果を返すケースは、コアリポジトリの [`tests/divergence.yaml`](https://github.com/libraz/formulon/blob/main/tests/divergence.yaml) に、理由と最後に確認した Excel のビルドとともに記録しています。記録のない差分は oracle テストで失敗します。

| ケース | Excel | Formulon | 理由 |
| --- | --- | --- | --- |
| 反復計算を無効にした状態の循環参照 | 1 つのセルに 0 を入れて残りを計算する。`A1=B1+1`、`B1=A1+1` は 1 と 0 になる | 循環に含まれるすべてのセルが `#REF!` | Excel の値はどのセルに 0 を入れるかで変わるので、正解の値が 1 つに決まりません。UI のないホストには警告ダイアログが出ないため、エラー値で知らせます。 |
| `=WEEKNUM(DATE(2024,1,1),99)` | Mac 版は 1、Windows 版は `#NUM!` | どちらのプロファイルでも `#NUM!` | `99` は有効な週の基準ではありません。Formulon は Windows 版と関数の仕様に従います。 |
| 印刷倍率 50% 以下の改ページ位置 | 改ページがページの寸法に従わなくなる | ページの寸法どおりに改ページする | 小さい倍率での Excel の改ページはページサイズから導けず、25% では逆に増えます。 |

`RATE` や `IRR` のような反復計算を使う財務関数は、ビット単位ではなく許容誤差（絶対誤差 1E-9 または相対誤差 1E-6）で比較しています。`=RATE(10,-100,1000)` は Excel では `-1.96E-10`、Formulon では 0 です。どちらも実質 0 ですが、同じ倍精度の値ではありません。

## 取得データを最新に保つ仕組み

- Formulon のプロファイルは 28 個あります。このうち 15 個（Mac の 14 ロケールすべてと Windows の `ja_JP`）は Excel で直接計測しています。残る 13 個の Windows プロファイルは、Mac での計測値に Windows ホストの規則を当てはめて推定しています。
- Mac の全ロケールの数式の取得データは、CI でテストとして実行します。取得データと結果が違えば、divergence の記録がない限りビルドが失敗します。対応するケースのない divergence の記録も失敗になります。
- ブック単位の挙動（ピボットテーブルと印刷レイアウト）は、Excel の自動操作が安定している Windows 版 Excel の `ja_JP` から取得しています。

取得の種類と失敗時の切り分けは [Oracle テスト](/ja/compatibility/oracle-testing)、プロファイルの考え方は[互換性モデル](/ja/compatibility/model)で説明しています。

## 保証していないこと

ここに挙げたケースが一致しても、あらゆるブックがあらゆる Excel のビルドと一致するわけではありません。`ja_JP` 以外の Windows プロファイルは推定値です。Excel 自体もビルドごとに挙動が変わります。お使いのブックが、上の例ほど細かく検証していない関数を使っている可能性もあります。利用者の環境に合うプロファイルを `setExcelProfileId()` で固定し、Excel での結果が分かっている自分のブックをいくつかテスト用に残してください。
